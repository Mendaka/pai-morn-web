# Project context

This is the Next.js rewrite of the Flutter Web frontend for Paimorn, a community guitar chord/lyrics songbook. It reuses the **existing** Firebase backend unchanged (project `song-and-chord`: Firestore, Auth, Storage, Cloud Functions, all security rules) — a frontend swap, not a data migration. The Android app stays native Flutter and is out of scope.

- Original Flutter project (source of truth for screens/behavior/algorithms to port): `D:\flutter_web\pai_morn_web`. The backend code (`functions/`, `firestore.rules`, `storage.rules`) also lives there and stays there.
- Migration plan (phases, what to port, which Cloud Functions become obsolete): `C:\Users\Asus\.claude\plans\streamed-tickling-crescent.md` — read it first.
- Built incrementally, phase by phase; the old Flutter web app stays live until cutover.
- Server-side Firestore reads use the client SDK with long-polling (`lib/firebase/server.ts`), not firebase-admin (no service-account key set up yet). Public pages must filter to `status == 'approved'` explicitly — Firestore rules alone also allow reading pending/rejected songs.

Design: matching the Flutter app's look is NOT required — the user explicitly said prettier is better and to use whatever Next.js/CSS can do. Port behavior and data shapes faithfully; feel free to improve visuals.

2026-10-06: BUG FIX (`public/sw.js`) — owner reported the exact symptom this service worker's own `isCacheableStatic` comment already describes verbatim ("เจอhtmlดิบๆ...ที่หน้า Chords หน้า Tuner จอโทรศัพ...บน desktop ไม่มีปัญหา"), and sent a screenshot confirming it: a completely unstyled page (bulleted nav list, underlined blue links, serif font — the browser's user-agent default, meaning the CSS request genuinely failed, not just loaded slowly — a `<link rel="stylesheet">` is render-blocking by default, so a SLOW fetch delays paint, it doesn't produce unstyled paint; only a fetch that actually ERRORS does).

Root cause: the static-asset cache-first handler had a bare, uncaught `await fetch(event.request)` with no error handling — when that fetch throws (a genuine transient drop, the exact "switching apps and coming back to a few seconds of flaky mobile network" scenario the handler's own comment already names as the reason this cache exists), the whole `event.respondWith()` promise rejects with nothing to fall back to (nothing was cached yet for that resource — it's often the FIRST time the browser's asking for it).
